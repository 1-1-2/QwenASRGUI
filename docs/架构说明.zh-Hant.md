# 架構說明

[简体中文](架构说明.md) · 繁體中文

本文描述目前程式碼的**實際行為**，供後續整理專案首頁時作為素材。不包含開發計畫、
排期或待辦事項；這些內容只在本機維護。

## 1. 視窗策略

啟動器 `app_webview.py` 先在本機 `127.0.0.1` 起一個隨機連接埠的
`WebViewServer`，再開啟瀏覽器視窗；前端只透過 HTTP 與 SSE 和後端溝通。

| 路徑 | 觸發條件 | 依賴 |
|---|---|---|
| Edge `--app` + `--inprivate` | **預設** | 系統內建 Microsoft Edge |
| 原生 WebView2 視窗 | 原始碼安裝時設 `QWENASR_NATIVE_WINDOW=1` | pywebview + pythonnet + .NET |
| 預設瀏覽器 | 系統沒有 Edge 時 | 任意瀏覽器 |

以前預設走原生 WebView2 視窗。散落的 DLL 從 ZIP 解壓後繼承
Mark-of-the-Web 標記，.NET 會拒絕載入被標記的 assembly，導致 pythonnet 失敗、
視窗靜默回退。當時的解決辦法是把全部內容打進單一 EXE（onefile），讓執行期
解壓到 `%TEMP%` 從而不帶標記。

現在預設走 Edge `--app`，根本不載入 .NET assembly，這條失敗鏈不再存在。
發行包因此不再捆綁 `webview` / `pythonnet` / `clr_loader`；`build_release.py`
把它們放進 `EXCLUDE_MODULES`。標題列配色 `_decorate_window_async()` 對兩種視窗
都適用，程式碼原樣保留。既然不再載入 .NET，散落 DLL 的 MOTW 問題也一併消失，
發行包隨之從 onefile 改為分層 onedir（§2）。

## 2. 打包形態

發行包由 `build_release.py` 以 PyInstaller **onedir** 建置，並依職責分層：

```text
QwenASR-WebView/
  QwenASR-WebView.exe   啟動器：執行期引導 + 視窗策略（內容穩定，可累積 SmartScreen 信譽）
  _internal/            程式本體：CPython 執行期、全部 .py、OpenVINO / ONNX Runtime /
                        音訊原生庫、前端資源
    ├─ models.json           模型下載清單的單一事實來源
    ├─ prompt_template.json / mel_filters.npy / silero_vad_v4.onnx / icon.ico
    └─ webview_assets/       前端 HTML / JS / CSS
  ffmpeg/ffmpeg.exe     選用，隨包附上
  ov_models/            模型權重（首次啟動按需下載，不內嵌）
  subtitles/            輸出 SRT
  longform_state/       中斷點與逐段 JSONL
  settings.json         持久化設定
```

以前是 onefile：每次啟動把約 200 MB 解壓到暫存目錄，每次更新都要替換整個大檔。
移除 pythonnet（§1）之後，促成 onefile 的 MOTW 失敗鏈不再存在，於是改為分層目錄——
啟動不再解壓，更新只需替換 `QwenASR-WebView.exe` 與 `_internal/` 兩項，使用者資料不動。

**路徑規則只有一條**，集中在 `app_paths.py`：

| 類別 | 位置 | 凍結時的值 |
|---|---|---|
| 使用者資料（設定、模型、字幕、中斷點、ffmpeg、crispasr） | 啟動器旁邊 | `app_dir()` = EXE 所在目錄 |
| 隨包唯讀資源（`models.json`、前端、VAD、Mel、範本、icon） | 資源根 | `resource_root()` = `_internal/`（onefile 下為 `_MEIPASS` 暫存目錄） |

這條規則不能用 `Path(__file__)` 實作：凍結後 `__file__` 指向**資源根**，
拿它當應用目錄會把設定與模型寫進 `_internal/`，下次更新就被覆蓋。
`resource_path()` 另外保留「啟動器旁也找得到」的相容查找，舊包與手動放置的檔案照常可用。
`tests/test_layout.py` 以偽造的 `sys.frozen` / `sys._MEIPASS` 把開發樹、onefile、
onedir 三種佈局逐一斷言，包括「使用者資料不得落在 `_internal/` 內」。

體積主要來自 CPython 標準庫、OpenVINO CPU plugin 與算子庫、ONNX Runtime、
NumPy / SciPy 的原生擴充及 GUI 相依。專案自身程式碼與前端只佔很小一部分。
模型權重（0.6B 約 1.2GB / 1.7B 約 4.4GB）刻意不內嵌。

`verify_onedir()` 檢查最終暫存目錄裡啟動器與 `_internal/` 的關鍵條目；`tools/verify_package.py`
另外斷言 `_internal/` 體積合理、使用者資料目錄都在啟動器旁、且純使用者資料目錄
（`subtitles/`、`longform_state/`、`ffmpeg/`）沒有混進 `_internal/`。

這裡有個容易踩坑的**同名雙用途目錄**：啟動器旁的 `ov_models/` 是使用者資料
（按需下載的辨識權重，更新時不動），而 `_internal/ov_models/` 是隨包唯讀資源
（Silero VAD、Mel filters，由 `STATIC_DATA` 經 `--add-data` 打進去）。
早期一條按目錄名一刀切的規則禁止 `ov_models/` 出現在 `_internal/` 內，與建置腳本和
`app.py::_find_vad_model()` 自相矛盾，曾讓 Windows 包在打完 198 MB ZIP 後才於校驗步失敗。
現在 `check_layout()` 按內容判定：該目錄只允許 VAD 與 mel 資源白名單，出現 `.bin` 權重即判失敗；
`tests/test_verify_package.py` 以偽造目錄樹覆蓋合法佈局與各類越界情形。函式內動態 import
的模組若漏列，不會在啟動時報錯，而是點到對應功能才 `ImportError`，所以這些校驗都是
建置時的硬性檢查。

另一個容易漏的體積來源是**介面層**：`app.py` 是 Tk 桌面版，WebView 版只複用它的推理解碼
核心（`ASREngine` / `ASREngine1p7B` / `RealtimeManager` 與上方那批純函式），從不實例化
`App`。但 PyInstaller 是靜態分析——只要看到 `import customtkinter`，就會把
customtkinter + tkinter + tcl/tk 全量收進包裡。因此整段 GUI（含 `import tkinter`）放在
`if not _WEBVIEW_BUILD:` 內，打包時由 `QWENASR_WEBVIEW_BUILD=1` 屏蔽；直接 `python app.py`
行為不變。這條界線由 `tests/test_webview_bundle.py` 以兩個子行程分別驗證。

啟動器本身還有一條與打包方式強相關的約束：`--windowed` 的 EXE **沒有主控台**，
`sys.stdout` / `sys.stderr` 是 `None`。開發模式永遠有終端，所以這類問題只在打包版暴露
（曾表現為關窗時 `AttributeError: 'NoneType' object has no attribute 'flush'`）。
`app_webview.hush_stdio()` 在匯入期換成寫 `launcher.log` 的替身，收尾 flush 改為盡力而為，
未捕捉例外統一寫日誌並彈窗。


進階主題（內容定址 manifest、差量、回滾、冷啟動基準、簽章與 SmartScreen）見 [打包與升級](打包與升級.zh-Hant.md)。

## 3. 統一串流資料流

所有輸入（GUI 單檔、批次、CLI、區網 API）都走同一條 `LongformRunner`
路徑，不再按時長分成兩套邏輯。

```text
音訊 / 影片檔案
  → ffmpeg 串流輸出 16 kHz / mono / s16le PCM（無 ffmpeg 時 WAV 走標準庫回退）
  → 滾動 VAD 緩衝（上限約 32 秒，與檔案長度無關）
  → 語音組 → processor_numpy 特徵 → OpenVINO INT8 IR → 文字
  → 每組立刻 append 寫入 SRT / JSONL + 儲存 checkpoint
  → SSE 推送結構化進度與即時字幕批次
```

記憶體占用與音訊長度無關：模型權重是固定的常駐成本，串流緩衝是固定小量，
字幕不攢到最後才寫盤。切分長度只影響上下文完整度與總耗時，不影響單段
張量形狀（特徵會被 pad 到模型匯出時的固定幀數），因此也不影響單段記憶體。

### 3.1 為什麼 1.7B 只能切 10 秒

`app.py` 裡 `ASREngine1p7B.max_chunk_secs = 10` **不是記憶體限制，也不是我們
隨意設的策略值**，而是目前下載的 INT8 IR 在**匯出時**把 audio_encoder 的
輸入幀數固定成 `T=1000`（10 秒）。送入更長的音訊會被靜默截斷並丟字，所以
執行期用 `min(設定值, 模型上限)` 夾緊，介面透過 `capabilities` 顯示
「目前生效 10s（模型上限 10s）」。0.6B 對應上限是 30 秒。

這個限制屬於**這一份模型檔**，不是 Qwen3-ASR 模型本身的能力邊界。要真正
支援 30 秒上下文，需要重新匯出 IR（改 `T`）、重生成 `prompt_template.json`，
並讓 decoder 的 position / RoPE 對齊——是模型轉換工程，執行期開關改不了。

另一個常見誤解：把切分長度從 10 秒調到 30 秒**不會增加記憶體占用**。特徵
張量在匯出時就固定了形狀，切片長度只改變上下文完整度與總耗時。

### 3.2 選用後處理：字級時間軸與說話人分離

這兩項在統一串流時沒有刪除，而是從舊的整段路徑移到 `postprocess.py`
的 `StreamEnhancer`，掛在同一條串流管道上：

| 功能 | 輸入 | 實作 |
|---|---|---|
| 字級時間軸（卡拉OK逐字） | 目前語音組的 PCM chunk + 辨識文字 | 寫暫存小 WAV，呼叫 `engine._align_chunk()`（chatllm ForcedAligner，CPU 子程序），把局部時間平移成全域時間後按行分配 `words` |
| 說話人分離 | 同一份 PCM chunk | 呼叫 `diar_engine._get_embedding()` 每段提一個 256 維向量，只攢向量不攢音訊；任務結束時聚類一次，按時間區間替字幕標 `說話者N` |

兩者都復用辨識時**已在記憶體裡**的 chunk，不需要第二次解碼，也不需要把
3–5 小時音訊重新讀進來。

失敗隔離是硬約束：SRT 由 Runner 逐組 append 寫盤，是唯一事實源；增強結果
另存 `*.rich.json`，`finalize()` 以 JSONL 為準重建行列表並原子替換。對齊器
崩潰、聚類報錯、增強檔寫不進去，都只記一條 note，**不會改動或刪除任何
一條 SRT 字幕**。介面橫幅也寫明「失敗不影響字幕」。開關勾選但對應模型未
安裝時，本次跳過並提示到模型頁下載，不自動下載 939 MB 的 ForcedAligner。

## 4. SSE 事件契約

`webview_server._EventHub` 把 `WebBackend` 的事件廣播給所有 `/api/events`
訂閱者。前端用 `window.QwenAPI.on(event, handler)` 接收。

| 事件 | 載荷 | 用途 |
|---|---|---|
| `progress` | `pct`, `status` | 相容舊版百分比進度條 |
| `progress-detail` | `pct`, `status`, `taskId`, `doneSec`, `totalSec`, `groups`, `etaSec`, `phase` | 已處理時間 / 總時長、分段數、剩餘時間、階段 |
| `segments` | `taskId`, `count`, `segments[{index,start,end,text}]` | 即時字幕；後端按 0.5 秒或 8 條節流成批 |
| `capabilities` | 生效切分長度、記憶體預估、`alignAvailable` / `diarAvailable` / `alignActive` / `diarActive` | 任務開始前告知增強功能是否可用、本次是否生效 |
| `vad-preview` | 段長分布、超上限比、極短段比、靜音比 | 切分預檢結果（前 5 分鐘，不跑辨識） |
| `download-retry` / `download-failure` / `download-source-switch` | `attempt`, `code`, `hint`, `file`, `provider` | 下載失敗分類與可執行的下一步 |
| `status` / `tunnel` | 模型狀態、通道狀態 | 狀態列與端點頁 |

下載類事件由 `downloader.py` 的 `set_download_event_hook()` 發出，經
`WebBackend._install_download_hook()` 轉接，不再 `print()` 到視窗版 EXE
看不見的 stdout。

`segments` 有節流是必要的：3–5 小時課程會產生上萬條字幕，逐條推事件會讓
WebView 渲染行程成為新的記憶體瓶頸。前端同樣把即時列表限制在最近 200 條，
並在使用者手動上捲時暫停自動跟隨。

進度條下方同時給出「時間 / 分段」與「百分比」兩種視圖；批次頁複用同一套
辨識參數，並把佇列總進度顯示在摘要裡。

## 5. 模型下載

`models.json` 是唯一事實來源，`model_catalog.py` 負責讀取與校驗、
`catalog_status()` 彙總狀態、`build_manifest_text()` 產生下載清單、
`import_local_bundle()` 匯入並校驗本機模型。始終使用標準庫 `urllib`，
不引入 `huggingface_hub` / `modelscope` / `hf_transfer`。

未對遠端檔案實測過的 `size_bytes` 與 `sha256` 一律為 `null`，介面顯示「未知」；
`size_hint` 是原始碼註解裡抄來的約略值，明確標註僅供參考且不用於進度計算。
鏡像切換只改寫 `huggingface.co` 前綴，GitHub 直鏈不受影響。

下載核心 `_download_file()` 支援斷點續傳、`Content-Length` 缺失時用 HEAD
探測或目錄給定大小兜底、重試退避、磁碟空間預檢、LFS pointer / HTML 錯誤頁
探測，以及把分類後的錯誤與來源切換透過事件回調送到介面。

## 7. 驗證邊界

CI 與本機回歸測試使用 mock ASR 引擎，不載入真實 OpenVINO 權重；驗證的是
調度層、落盤、中斷點、下載鏈路與前後端接線，不驗證辨識準確率。真實模型推論
需要在使用者本機執行。
