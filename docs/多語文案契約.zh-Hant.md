# 多語文案契約（H6/H7）

繁體中文 · [简体中文](多语文案契约.md)

> 本文只描述使用者可見文案的產生與翻譯規則，不涉及辨識邏輯、中斷點或打包。

## 先說邊界

- **不是所有文字都會翻譯**。例外堆疊、檔案路徑、模型名稱、使用者填寫的提示詞、執行紀錄屬於自由文字，無法窮舉，按約定保留原文（英文介面下也會看到中文）。
- **canonical value 不變**。下拉選單的 `value`、模型名、核心名、語言代號仍是原始字串，i18n 只作用於顯示文字，因此切換介面語言不會改變任何功能行為。
- **三語文案由人工維護**，沒有機器翻譯，也沒有執行期轉換服務。新增一條可列舉文案必須同時補齊三種語言，否則 CI 直接失敗。

## 為什麼廢棄舊方案

初版把後端送來的繁體中文整串拿來本地化：繁體原樣、簡體按「逐字表」替換、英文查整串短語字典，未命中就顯示原文。三個問題：

1. 簡繁差異不只是字形，更多是**用詞**：「記憶體／内存」「預設／默认」「透過／通过」「檔案／文件」「網路／网络」。逐字替換會產出簡體讀者不會寫的句子。
2. 英文字典只收了短語，長描述、帶變數的句子、後來新增的文案全部露中文。
3. 逐字表本身是手寫字串，混入了 3 字元片段，導致後續配對整體錯位——「記憶體不足」曾被渲染成「建續不足」。

使用者裁決：接受應有的修改代價，改為「後端發 `key + vars`，前端三語獨立人工文案」。

## 契約結構

後端 `ui_text.py` 維護 `TEMPLATES`：`key -> 繁體模板`，是**唯一事實來源**。`msg(key, **vars)` 回傳：

```json
{"k": "msg.backend.same", "v": {"label": "CPU · OpenVINO INT8"}, "t": "「CPU · OpenVINO INT8」已是目前使用的核心。"}
```

| 欄位 | 作用 |
|---|---|
| `k` | 穩定文案識別，語意變了就換新 key，不要沿用 |
| `v` | 變數，值可以是字串、數字，或巢狀的 `msg()` |
| `t` | 繁體渲染結果，供執行紀錄、舊介面消費、前端降級兜底 |

前端 `webview/js/i18n.js` 的 `M` 字典保存 `key -> [繁體, 簡體, English]`，全部人工撰寫。`I18N.L()` 是唯一渲染入口：見到 `k` 就查字典並把 `v` 遞迴插值；見到 `parts` 就逐段渲染後拼接；見到純字串就走兜底。現有 19 處呼叫點無需改動。

**變數插值的位置可以按語言變化**，這正是結構化的價值：

| 語言 | `msg.backend.same` |
|---|---|
| 繁體 | 「CPU · OpenVINO INT8」已是目前使用的核心。 |
| 簡體 | 「CPU · OpenVINO INT8」已是当前使用的核心。 |
| English | CPU · OpenVINO INT8 is already the active engine. |

## 兜底規則（自由文字）

`fallback()` 處理沒有 key 的字串：

- 繁體：原樣。
- 簡體：**先按詞表 `W2S_WORDS` 替換用詞**（按長度降冪），再按 `S2S` 單字表轉換剩餘字元。字元表由真實轉換器逐字產生，只保留 1:1 對應，避免手寫配對錯位。
- 英文：`EN_MAP` 精確短語命中則替換，否則保留原文。

執行紀錄刻意不翻譯：排障時需要與後端實際輸出逐字對應。後端 `_emit()` 在寫入紀錄前用 `plain()` 把結構化值壓平為 `t`。

## 覆蓋清單

`ui_text.py` 的鍵分組：`profile.*`（基礎模式用途卡）、`state.*` / `health.*`（啟動自檢）、`device.*`（裝置與 GPU 診斷）、`msg.*`（核心／加速版本／模型選擇回饋）、`status.*`、`progress.*`（下載與轉錄進度）、`warn.*`、`hw.*`、`accel.*`（加速版本選項與推薦理由）。

`downloader.py` 的加速版本資料被 CTk 版共用，因此**保留原有繁體字串**，另增 `i18n_reason` 與每個 option 的 `i18n` 欄位；`WebBackend.get_accel()` 負責把它們轉成結構化訊息送給 WebView，CTk 不受影響。

前端靜態介面文案仍在 `D` 字典（`data-i18n` 屬性驅動），與 `M` 字典分開：前者是 HTML 裡的固定文字，後者是後端執行期產生的文字。

## 新增一則文案

1. 在 `ui_text.py` 的 `TEMPLATES` 加繁體模板，變數寫成 `{name}`。
2. 在 `webview/js/i18n.js` 的 `M` 加同 key 的三語陣列，佔位符必須逐一對應。
3. 後端改用 `_t.msg(key, ...)`；需要紀錄或字串拼接時用 `_t.plain()`。
4. 跑 `python tests/test_i18n_contract.py`。缺任一種語言、佔位符不一致、英文混入漢字、後端送了未註冊的 key，都會在這裡失敗。

## 回歸與 CI

`tests/test_i18n_contract.py` 用 Node 載入**真實** `i18n.js`，並用一個獨立子行程以偽 `app` core 驅動**真實**後端 API，共校驗：

- 前後端 key 集合完全一致（無遺漏、無孤兒）；
- 每個 key 三語非空，`{placeholder}` 集合在後端模板與三種語言中一致；
- 前端繁體文案與後端 `TEMPLATES` 逐字相同（單一事實來源）；
- 英文文案不含 CJK；
- 簡體用詞確實不同（不是逐字轉換），且兜底不再產生亂碼；
- 結構化值、巢狀訊息、`parts` 拼接、未知 key 降級在三語下都正確；
- 10 個真實後端 API 的回傳值可 JSON 序列化，且送出的每個 key 都已註冊。

`tests/test_ui_ops.py` 另做靜態接線檢查。兩者都進入 `ci.yml`。

## 已知邊界

- 自由文字在英文介面保留中文，這是刻意設計，不是漏翻。
- `get_status().backend`、`arch` 等 canonical 顯示名不做翻譯（本身多為英文型號名）。
- 單字表由轉換器產生，個別破音字在極罕見的自由文字裡可能不貼切；可列舉文案不受影響，因為走的是人工三語。
