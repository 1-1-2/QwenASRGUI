# 多语文案契约（H6/H7）

简体中文 · [繁體中文](多語文案契約.zh-Hant.md)

> 本文只描述用户可见文案的生成与翻译规则，不涉及识别逻辑、断点或打包。

## 先说边界

- **不是所有文字都会翻译**。异常堆栈、文件路径、模型名、用户填写的提示词、运行日志属于自由文本，无法穷举，按约定保留原文（英文界面下也会看到中文）。
- **canonical value 不变**。下拉框的 `value`、模型名、核心名、语言代号仍是原始字符串，i18n 只作用于显示文本，因此切换界面语言不会改变任何功能行为。
- **三语文案由人工维护**，没有机器翻译，也没有运行时转换服务。新增一条可枚举文案必须同时补齐三种语言，否则 CI 直接失败。

## 为什么废弃旧方案

初版把后端发来的繁体中文整串拿来本地化：繁体原样、简体按「逐字表」替换、英文查整串短语字典，未命中就显示原文。三个问题：

1. 简繁差异不只是字形，更多是**用词**：「記憶體／内存」「預設／默认」「透過／通过」「檔案／文件」「網路／网络」。逐字替换会产出简体读者不会写的句子。
2. 英文字典只收了短语，长描述、带变量的句子、后来新增的文案全部露中文。
3. 逐字表本身是手写字符串，混入了 3 字符片段，导致后续配对整体错位——「記憶體不足」曾被渲染成「建續不足」。

用户裁决：接受应有的修改代价，改为「后端发 `key + vars`，前端三语独立人工文案」。

## 契约结构

后端 `ui_text.py` 维护 `TEMPLATES`：`key -> 繁体模板`，是**唯一事实源**。`msg(key, **vars)` 返回：

```json
{"k": "msg.backend.same", "v": {"label": "CPU · OpenVINO INT8"}, "t": "「CPU · OpenVINO INT8」已是目前使用的核心。"}
```

| 字段 | 作用 |
|---|---|
| `k` | 稳定文案标识，语义变了就换新 key，不要复用 |
| `v` | 变量，值可以是字符串、数字，或嵌套的 `msg()` |
| `t` | 繁体渲染结果，供运行日志、旧接口消费、前端降级兜底 |

前端 `webview/js/i18n.js` 的 `M` 字典保存 `key -> [繁体, 简体, English]`，全部人工撰写。`I18N.L()` 是唯一渲染入口：见到 `k` 就查字典并把 `v` 递归插值；见到 `parts` 就逐段渲染后拼接；见到纯字符串就走兜底。现有 19 处调用点无需改动。

**变量插值的位置可以按语言变化**，这正是结构化的价值：

| 语言 | `msg.backend.same` |
|---|---|
| 繁体 | 「CPU · OpenVINO INT8」已是目前使用的核心。 |
| 简体 | 「CPU · OpenVINO INT8」已是当前使用的核心。 |
| English | CPU · OpenVINO INT8 is already the active engine. |

## 兜底规则（自由文本）

`fallback()` 处理没有 key 的字符串：

- 繁体：原样。
- 简体：**先按词表 `W2S_WORDS` 替换用词**（按长度降序），再按 `S2S` 单字表转换剩余字符。字符表由真实转换器逐字生成，只保留 1:1 映射，避免手写配对错位。
- 英文：`EN_MAP` 精确短语命中则替换，否则保留原文。

运行日志刻意不翻译：排障时需要与后端实际输出逐字对应。后端 `_emit()` 在写入日志前用 `plain()` 把结构化值压平为 `t`。

## 覆盖清单

`ui_text.py` 的键分组：`profile.*`（基础模式用途卡）、`state.*` / `health.*`（启动自检）、`device.*`（设备与 GPU 诊断）、`msg.*`（核心／加速版本／模型选择反馈）、`status.*`、`progress.*`（下载与转录进度）、`warn.*`、`hw.*`、`accel.*`（加速版本选项与推荐理由）。

`downloader.py` 的加速版本元数据被 CTk 版共用，因此**保留原有繁体字符串**，另增 `i18n_reason` 与每个 option 的 `i18n` 字段；`WebBackend.get_accel()` 负责把它们转成结构化消息发给 WebView，CTk 不受影响。

前端静态界面文案仍在 `D` 字典（`data-i18n` 属性驱动），与 `M` 字典分开：前者是 HTML 里的固定文本，后者是后端运行时产生的文本。

## 新增一条文案

1. 在 `ui_text.py` 的 `TEMPLATES` 加繁体模板，变量写成 `{name}`。
2. 在 `webview/js/i18n.js` 的 `M` 加同 key 的三语数组，占位符必须逐一对应。
3. 后端改用 `_t.msg(key, ...)`；需要日志或字符串拼接时用 `_t.plain()`。
4. 跑 `python tests/test_i18n_contract.py`。缺任意一种语言、占位符不一致、英文混入汉字、后端发了未注册的 key，都会在这里失败。

## 回归与 CI

`tests/test_i18n_contract.py` 用 Node 加载**真实** `i18n.js`，并用一个独立子进程以伪 `app` core 驱动**真实**后端 API，共校验：

- 前后端 key 集合完全一致（无遗漏、无孤儿）；
- 每个 key 三语非空，`{placeholder}` 集合在后端模板与三种语言中一致；
- 前端繁体文案与后端 `TEMPLATES` 逐字相同（单一事实源）；
- 英文文案不含 CJK；
- 简体用词确实不同（不是逐字转换），且兜底不再产生乱码；
- 结构化值、嵌套消息、`parts` 拼接、未知 key 降级在三语下都正确；
- 10 个真实后端 API 的返回值可 JSON 序列化，且发出的每个 key 都已注册。

`tests/test_ui_ops.py` 另做静态接线检查。两者都进入 `ci.yml`。

## 已知边界

- 自由文本在英文界面保留中文，这是刻意设计，不是漏翻。
- `get_status().backend`、`arch` 等 canonical 显示名不做翻译（本身多为英文型号名）。
- 单字表由转换器生成，个别多音字在极罕见的自由文本里可能不贴切；可枚举文案不受影响，因为走的是人工三语。
