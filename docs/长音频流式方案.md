# 长音频流式方案（B 方案）

> 本文件为长音频改造新增文档，统一使用简体中文。
> 面向 1~5 小时网课 / 会议录音、纯 CPU + OpenVINO INT8、无独立显卡的机器。

## 一句话

把 `webview_backend.transcribe()` 里「整段加载音频 + 末尾一次性写盘」的调度层，换成
**ffmpeg 流式 PCM → 滚动 VAD 分组 → 每组立刻落盘 + 断点记录**。ASR 引擎、前端、
SSE 协议都不改。

## 为什么要改

### 内存呈 8~10 秒周期的锯齿

不是内存泄漏，是逐 token 自回归解码在反复分配大张量：

| 现象 | 源码位置 | 机制 |
|---|---|---|
| 大张量反复分配/释放 | `app.py:967-1003` | 1.7B KV-cache 的 `past_k` / `past_v` 形状 `(28,1,8,L,128)` float32，L≈405（`prompt_template.json`：prefix 9 + audio 390 + suffix 6）→ 单个 44.3 MiB、两个 88.6 MiB；每生成 1 个 token 就换一轮。生成 100 tokens 累计约 8.65 GiB 内存周转（不是同时占用） |
| 立刻归还操作系统 | NumPy 大数组走 mmap / VirtualAlloc | 释放即 munmap，RSS 骤降；小对象走堆不归还 → 形成锯齿而非平滑曲线 |
| 8~10 秒周期 | `app.py:709-735` | 一个 VAD 语音组的解码时长，函数返回时局部大数组集体出作用域 |
| 每段 mel 固定补到 30s | `processor_numpy.py:103-130` | 中间量约 30~40 MB/段，是叠加项而非 GB 级主因 |

0.6B 用 stateful decoder（`app.py:663-666`），KV 由 OpenVINO 内部管理，锯齿会小很多；
看到「几个 G」的波动通常说明当前选的是 1.7B。

### CPU 只有 20% 左右

同样是设计取舍：`app.py:564` 写死 `PERFORMANCE_HINT = "LATENCY"`；
`model_tab.py:317` 默认「自動（省電）」→ `cpu_threads=0` → 不设 `INFERENCE_NUM_THREADS`；
每生成 1 个 token 要跑两次 OV infer（embedder + decoder），全是小算子 + `np.argmax`
大词表 + Python 循环，属于**延迟 bound**而非算力 bound；`app.py:530` 的 `_lock`
让多线程并发只会排队。

所以本方案**不靠并发提速**，靠的是「不重跑、不丢结果、内存峰值不随文件变长」。

## 改了什么

| 文件 | 作用 |
|---|---|
| `longform_runner.py` | 新增。流式 PCM、滚动 VAD 分组、增量 SRT/JSONL、SQLite/JSON 双写断点、取消 |
| `webview_backend.py` | 新增长音频判定与分支；`cancel()` 同步通知 Runner |
| `cli_mode.py` | 新增 `--longform` / `--no-resume` |
| `tests/make_fixture.py` | 新增。把仓库内的公开短音频离线拼成几分钟测试集 |
| `tests/test_longform_runner.py` | 新增。20 项回归（含真实 ffmpeg 流式、可选真实 VAD） |
| `tests/test_integration.py` | 新增。8 项后端接线测试（mock 掉 GUI 依赖） |
| `.github/workflows/ci.yml` | 新增。push / PR 自动跑语法检查与两套测试 |

**单 worker 串行是硬约束**：`ASREngine.transcribe()` 自带互斥锁，多线程只排队；
多进程则每份进程各载一套 IR，内存与锯齿叠加。

## 怎么用

### 图形界面（无需操作）

音频时长 ≥ `longform_minutes`（默认 **20 分钟**，可在 `settings.json` 调整）时自动启用。
进入流式模式会在进度区提示「长音频流式模式」。中途点取消会保存断点，
对**同一个文件**再次开始即可续跑。

### 命令行

```bash
# 强制启用（不依赖时长判定）
QwenASR-WebView.exe transcribe course.mp4 --longform --json

# 忽略已有断点，从头重跑
QwenASR-WebView.exe transcribe course.mp4 --longform --no-resume -o course.srt

# 源码方式
python app_webview.py transcribe course.mp4 --longform --json
```

CLI 的输出契约不变：`{"segments":[...], "srtPath":"..."}`，进度仍走 stderr。

### 断点文件位置

`<程序目录>/longform_state/`：

- `checkpoints.db` / `checkpoints.json` — 帧号、SRT 序号、状态（双写镜像，SQLite 失败自动降级）
- `<task_id>.segments.jsonl` — 每条字幕的结构化副本，便于校对与重排
- 最终 SRT 仍在 `subtitles/`

`task_id` 由源文件绝对路径的 sha1 前 12 位生成：同文件续跑、不同文件互不干扰。

## 能力回退清单

| 能力 | 流式模式 | 说明 |
|---|---|---|
| VAD 切片 / 长音频 | ✅ 保留且更强 | 流式分段、断点续跑、取消 |
| 上下文提示 `hint` | ✅ 保留 | 已透传 `context=` |
| 简繁转换 / 输出 `.txt` | ✅ 保留 | 由原有收尾逻辑处理 |
| 实时进度 SSE | ✅ 保留 | `(pct,status)` 契约不变 |
| 词级时间轴 / 卡拉OK 逐字 | ❌ 回退为行级 | 不写 `_last_segments_rich`，前端走 SRT 解析 |
| 说话人分离 / 声纹 | ❌ 未接 | `diarize` / `n_speakers` 未透传 |
| ForcedAligner 精确对齐 | ❌ 未接 | 时间轴按字符数线性分配 |

如果后三项是刚需，请先用短音频（< 20 分钟）走原路径，或手动加
`opts["longform"]=False` 关闭自动判定。

## 已知限制

1. **真实模型推理未在本环境验证**。沙箱无法访问 Hugging Face / ModelScope，
   仓库里只有 `ov_models/mel_filters.npy`，没有 IR 权重。测试用 mock ASR 引擎
   验证调度层；请在本地装好 0.6B / 1.7B INT8 模型后，先拿 10 分钟样本试跑一次。
2. **断点边界最多损失 1 个语音组**（≤ `max_chunk_secs` 秒）：恢复时 ffmpeg 精确
   seek 到断点帧，但 VAD 的 h/c 状态会重置。测试里 1.2 分钟音频「完整跑 30 条」
   对比「取消后续跑 39 条」会出现条数差异，属正常边界行为。要求零丢失请按
   20~30 分钟预先切分文件。
3. **1.7B 的 `max_chunk_secs` = 10**（`app.py:943`，audio_encoder 导出固定 T=1000），
   段数约为 0.6B 的三倍，长音频总耗时更久。
4. **SQLite 降级**：Windows + 杀毒软件 / OneDrive 目录下可能写入失败，
   `Checkpoint` 会自动降级为 JSON 镜像，进度不丢。
5. 原有代码与文案保持繁体未动；本次改造新增的文件、注释、文档与提交信息
   一律使用简体中文。

## 独立调优：把 CPU 拉起来

「模型」页 → CPU 效能：默认「自動（省電）」，可切「全速（N 執行緒）」，
**改完必须重新载入模型**（`model_tab.py:330` 也有提示）。对应 `app.py:567`
设置 `INFERENCE_NUM_THREADS`。

注意 `os.cpu_count()` 会把 E 核算进去，Intel 混合架构全塞可能因 P/E 核同步反而变慢；
若变慢就手动把 `cpu_threads` 调成物理大核数。线程数只改善矩阵乘部分，
别期待等比提速。这与本次流式改造完全正交，可先单独试。
