# 打包與升級

繁體中文 · [简体中文](打包与升级.md)

> **Important · 未簽章**：發行包的啟動器沒有程式碼簽章。首次執行 Windows SmartScreen
> 會提示「Windows 已保護您的電腦」→「其他資訊」→「仍要執行」。分層佈局讓啟動器內容穩定，
> 不再每次更新都換 EXE，有利於信譽累積；但這**不能取代簽章**，正式散佈需要程式碼簽章憑證。

## 為什麼是 onedir

| 形態 | 啟動 | 更新 | 代價 |
|---|---|---|---|
| onefile（舊） | 每次解壓約 200 MB 到 `%TEMP%` | 整包替換 | 冷啟動慢、Defender 掃暫存目錄、SmartScreen 信譽每次歸零 |
| onedir 分層（目前） | 直接載入已就位的檔案 | 只替換 EXE + `_internal/` + `manifest.json` | 是資料夾，不能只拷 EXE |

移除 pythonnet 之後，當年迫使 onefile 的 MOTW 失敗鏈（散落 DLL 被標記、.NET 拒載）已不存在。
路徑規則集中在 `app_paths.py`，詳見 [架構說明](架構說明.zh-Hant.md) §2。

## 目錄契約

```text
QwenASR-WebView.exe    啟動器                    ┐
_internal/             程式本體、相依、前端      ├─ 受管內容（manifest 覆蓋，更新時替換）
manifest.json          內容定址清單（SHA256）    ┘
ov_models/ subtitles/ longform_state/ ffmpeg/
crispasr/ chatllm/ GPUModel/ settings.json
app.lock app.prev/ 使用說明.txt build_manifest.json   ── 使用者資料 / 輔助檔案（更新時不動）
```

`manifest.json` 只記錄受管內容。`USER_DATA` 集合在 `release_manifest.py` 中定義，
`build_manifest()` 會明確跳過它們 —— 使用者的 4.4 GB 模型與中斷點永遠不會被列舉或覆蓋。

## 建置

```bash
python build_release.py --version 2.0.0 --sha <short-sha>
```

`build_release.py` 依序：`--onedir` 打包 → 整樹複製到 `release_pkg/QwenASR-WebView/` →
**`slim_openvino()` 精簡 OpenVINO** → 產生 `manifest.json` → `verify_onedir()` 檢查關鍵條目 → 組 ZIP。

### 體積：哪些必要，哪些可刪

模型權重不內嵌（1.2～4.4 GB，按需下載），因此包體主要由執行期依賴構成。目前可刪的只有
OpenVINO 的**未使用元件**：

| 元件 | 體積 | 需要嗎 |
|---|---|---|
| `openvino_intel_cpu_plugin.dll` | 40.5 MB | **必要**（唯一推理裝置） |
| `openvino.dll` + 依賴外掛 + `tbb*.dll` | ~26 MB | **必要** |
| `openvino_intel_gpu_plugin.dll` | 30.9 MB | 不需要：本專案恆用 CPU |
| `openvino_intel_npu_plugin.dll` | 4.0 MB | 不需要 |
| TensorFlow / ONNX / PyTorch / Paddle / TFLite / JAX 前端 | ~14 MB | 不需要：只載入 IR |
| `*.lib`（匯入庫）、`cache.json`（裝置快取） | 16.5 MB | 不需要：編譯期產物／可重建 |
| `include/`（C++ 標頭檔）、`*.pyi`（型別存根） | 6 MB | 不需要：寫程式／編譯時才讀，`import` 不碰 |

實測 `openvino/` 目錄 **132 MB → 61 MB（省 71 MB）**。保護措施：

- 認不出目錄佈局（缺 CPU 外掛／核心 DLL／IR 前端）就**整體跳過**，寧可不動也不打壞包；
- `tools/verify_package.py` 的 `check_openvino_slim()` 斷言 CPU 路徑在位、GPU/NPU 不在位；
- `python build_release.py --no-slim` 一鍵回復完整元件。

**SciPy 已整體移除（省 69 MB）**。它原本只服務兩個函式：

| 原用途 | 替換實作 | 為什麼可以換 |
|---|---|---|
| `linkage` / `fcluster`（說話者分群） | `cluster_core.py` 自帶 average-linkage | 演算法與 Lance-Williams 更新公式完全照搬；`tests/test_cluster.py` 用 300 組隨機資料與 SciPy 對拍，Z 矩陣與兩種 `fcluster` 語意**逐位一致** |
| `resample_poly`（重採樣備援） | `audio_io._resample_fft` 頻域理想低通 | soxr 才是主力路徑；頻域低通在抗混疊上嚴格更強（10 kHz 混疊到 16 kHz 取樣時 RMS = 0） |

代價是 `scipy/` 49.7 MB + `scipy.libs/` 19.3 MB 不再進包。三道守衛：`EXCLUDE_MODULES` 明確排除、
`make_package()` 斷言包內不得出現 `scipy*` 目錄、發佈建置的 CI 環境**刻意不安裝 scipy**。

另有兩項**刻意不刪**：`onnxruntime`（`app.py` 無條件匯入，說話者分離依賴它）、
`tokenizers`（`--collect-all`，Qwen 分詞器執行期必需）。

介面層也做過隔離：`app.py` 的 Tk 介面（customtkinter + tkinter + tcl/tk）在 WebView 版完全用不到，
過去因頂層 `import customtkinter` 被靜態分析連帶收進包；現在整段 GUI 放在
`if not _WEBVIEW_BUILD:` 裡，`python app.py` 不受影響。

> **⚠ 建置期開關不能當執行期判據**（2026-11-11 的真實事故）
>
> `QWENASR_WEBVIEW_BUILD=1` 只是傳給 **PyInstaller 分析子行程**的環境變數，
> 不會跟著 exe 發出去。而 `app.py` 曾經用它判斷「我是不是 WebView 版」，
> 於是 exe 在使用者機器上執行時該變數不存在 → `False` → 真的去 `import tkinter`
> → 包裡刻意沒帶 tkinter → 一啟動就死：
>
> ```
> RuntimeError: 無法載入本程式核心模組（webview_server）：No module named 'tkinter'
> ```
>
> 正解是另有一條**執行期**判據：`sys.frozen`（凍結版只有 `app_webview.py` 一個入口，
> 發行包又刻意不帶 tkinter/tcl）。現在由 `_is_webview_build()` 兩者取或。
>
> 更值得記住的是**為什麼這個 bug 能躲過好幾輪排查**：`tools/smoke_test.py` 的
> 診斷腳本與 `tests/test_release_env.py` 的探針都主動設了該變數，等於替 exe 補上了
> 那個不存在的環境變數 —— 模擬條件與真機不一致，於是「必崩」被一路測成「全綠」。
> 現在兩處都改成 `sys.frozen = True` 且**明確不設**該變數。
>
> 通用教訓：**凡是「打包時決定、執行時消費」的開關，都要確認它真的被寫進了產物**。

`tools/verify_package.py` 額外校驗分層結構、`_internal/` 體積、manifest，以及
`check_layout()` 定義的目錄契約：使用者資料目錄必須在啟動器旁，純使用者資料目錄不得進入
`_internal/`，`_internal/ov_models/` 則允許且只允許隨包 VAD / Mel 唯讀資源
（同名雙用途目錄，詳見 [架構說明](架構說明.zh-Hant.md)）。這套契約由 `tests/test_verify_package.py`
在 CI 與打包前回歸中覆蓋，避免「包已經打出來了、校驗才失敗」。

## 校驗 / 差量 / 更新 / 回滾

```bash
# 校驗發行包是否被改動
python release_manifest.py verify --root release_pkg/QwenASR-WebView

# 看兩個版本之間到底要傳哪些檔案
python release_manifest.py diff --old <舊包> --new <新包>

# 安裝新版本（自動備份舊版到 app.prev/，使用者資料原樣保留）
python release_manifest.py apply --new <新包> --install <安裝目錄>

# 出問題就回滾
python release_manifest.py rollback --install <安裝目錄>
```

`apply` 先用 `verify` 校驗新包，不通過就**在改動任何檔案之前**拋錯。
替換過程中若複製失敗會自動呼叫 `rollback()`。`app.prev/` 保存上一版的 EXE、
`_internal/` 與 `manifest.json`。

`diff` 按 SHA256 比較，輸出 `added / changed / removed / unchanged` 與 `changedBytes`。
**自動更新策略（已定案：A 方案）**：主線 WebView 版「檢查更新」只打開發行頁，由使用者手動下載 ZIP 覆蓋；不比對版本、不下載、不替換。`updater.py` 裡那套整包自動更新屬於停更的 CTk 版，WebView 不呼叫；`release_manifest.py` 的差量散佈是獨立命令列工具（`verify` / `diff` / `apply` / `rollback`），**未接入 UI，也未接入 `updater.py`**。因此準確說法不是「沒有自動更新機制」，而是「不投入把差量工具接進主線、替換 CTk 遺留機制的整套工程」。在未簽名 + 上游無 License 的前提下，整套改造（需重寫 `updater.py`、Release 附 manifest、前端進度／重啟 UI、helper 行程處理執行中檔案鎖、程式碼簽章與金鑰管理、Windows 實機回歸）風險大於收益，故維持 A 方案。

## 平滑升級（G4）

`tests/test_release_manifest.py` 用真實檔案系統驗證：更新前寫入 `settings.json`、
`subtitles/*.srt`、`ov_models/*.bin`、`longform_state/checkpoint.json`，
`apply` 後逐項斷言內容不變，再 `rollback` 斷言舊 payload 恢復且使用者資料仍然完好。
這是「舊設定 / 舊模型目錄 / 舊中斷點無縫接管」的可重現證據。

## 冷啟動基準（G6）

```bash
python app_webview.py --selftest
```

輸出一行 JSON：`constructMs`、`serverStartMs`、`healthRoundTripMs`、`resourceResolveMs`、
`layout`、`frozen`。無 GUI 相依的環境會把 server 部分標註為 `skipped`，仍能當 smoke test 用。

**邊界**：不包含 OS 行程建立、視窗建立、Edge 啟動。那些只能在目標 Windows 機器上用
「雙擊 → 視窗出現」計時。onedir 相對 onefile 的冷啟動收益目前**未實測**。

## 簽章與 SmartScreen（G8/G9）

- 現狀：**未簽章**。EXE 由 PyInstaller 產生，未走 Authenticode。
- 使用者操作：SmartScreen 提示時點「其他資訊」→「仍要執行」；不要執行來源不明的同名 EXE。
- 緩解：啟動器內容穩定 → 同一檔案的信譽可累積；`manifest.json` 讓使用者可自行核對 SHA256。
- 正式方案：OV / EV 程式碼簽章憑證 + `signtool sign /fd SHA256 /tr <timestamp> /td SHA256`，
  並對 ZIP 附一份 SHA256 校驗和。**這一步還沒做**，屬於發行流程待辦。
- 請勿只拷走 `QwenASR-WebView.exe`；缺少 `_internal/` 會直接啟動失敗。
