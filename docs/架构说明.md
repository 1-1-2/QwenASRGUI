# 架构说明

简体中文 · [繁體中文](架构说明.zh-Hant.md)

本文描述当前代码的**实际行为**，供后续整理项目主页时作为素材。不包含开发计划、
排期或待办事项；这些内容只在本地维护。

## 1. 窗口策略

启动器 `app_webview.py` 先在本机 `127.0.0.1` 起一个随机端口的
`WebViewServer`，再打开浏览器窗口；前端只通过 HTTP 与 SSE 与后端通信。

| 路径 | 触发条件 | 依赖 |
|---|---|---|
| Edge `--app` + `--inprivate` | **默认** | 系统自带 Microsoft Edge |
| 原生 WebView2 窗口 | 源码安装时设 `QWENASR_NATIVE_WINDOW=1` | pywebview + pythonnet + .NET |
| 默认浏览器 | 系统没有 Edge 时 | 任意浏览器 |

以前默认走原生 WebView2 窗口。散落的 DLL 从 ZIP 解压后继承
Mark-of-the-Web 标记，.NET 会拒绝加载被标记的 assembly，导致 pythonnet 失败、
窗口静默回退。当时的解决办法是把全部内容打进单个 EXE（onefile），让运行时
解压到 `%TEMP%` 从而不带标记。

现在默认走 Edge `--app`，根本不加载 .NET assembly，这条失败链不再存在。
发行包因此不再捆绑 `webview` / `pythonnet` / `clr_loader`；`build_release.py`
把它们放进 `EXCLUDE_MODULES`。标题栏配色 `_decorate_window_async()` 对两种窗口
都适用，代码原样保留。既然不再加载 .NET，散落 DLL 的 MOTW 问题也一并消失，
发行包随之从 onefile 改为分层 onedir（§2）。

## 2. 打包形态

发行包由 `build_release.py` 用 PyInstaller **onedir** 构建，并按职责分层：

```text
QwenASR-WebView/
  QwenASR-WebView.exe   启动器：运行时引导 + 窗口策略（内容稳定，可累积 SmartScreen 信誉）
  _internal/            程序本体：CPython 运行时、全部 .py、OpenVINO / ONNX Runtime /
                        音频原生库、前端资源
    ├─ models.json           模型下载清单的单一事实源
    ├─ prompt_template.json / mel_filters.npy / silero_vad_v4.onnx / icon.ico
    └─ webview_assets/       前端 HTML / JS / CSS
  ffmpeg/ffmpeg.exe     可选，随包附带
  ov_models/            模型权重（首次启动按需下载，不内嵌）
  subtitles/            输出 SRT
  longform_state/       断点与逐段 JSONL
  settings.json         持久化设置
```

以前是 onefile：每次启动把约 200 MB 解压到临时目录，每次更新都要替换整个大文件。
去掉 pythonnet（§1）之后，促使 onefile 的 MOTW 失败链不再存在，于是改为分层目录——
启动不再解压，更新只需替换 `QwenASR-WebView.exe` 与 `_internal/` 两项，用户数据不动。

**路径规则只有一条**，集中在 `app_paths.py`：

| 类别 | 位置 | 冻结时的取值 |
|---|---|---|
| 用户数据（设置、模型、字幕、断点、ffmpeg、crispasr） | 启动器旁边 | `app_dir()` = EXE 所在目录 |
| 随包只读资源（`models.json`、前端、VAD、Mel、模板、icon） | 资源根 | `resource_root()` = `_internal/`（onefile 下为 `_MEIPASS` 临时目录） |

这条规则不能用 `Path(__file__)` 实现：冻结后 `__file__` 指向**资源根**，
拿它当应用目录会把设置和模型写进 `_internal/`，下次更新就被覆盖。
`resource_path()` 另外保留了「启动器旁也能找到」的兼容查找，旧包与手工放置的文件照常可用。
`tests/test_layout.py` 用伪造的 `sys.frozen` / `sys._MEIPASS` 把开发树、onefile、
onedir 三种布局逐一断言，包括「用户数据不得落在 `_internal/` 内」。

体积主要来自 CPython 标准库、OpenVINO CPU plugin 与算子库、ONNX Runtime、
NumPy / SciPy 的原生扩展及 GUI 依赖。项目自身代码和前端只占很小一部分。
模型权重（0.6B 约 1.2GB / 1.7B 约 4.4GB）刻意不内嵌。

`verify_onedir()` 检查最终暂存目录里启动器与 `_internal/` 的关键条目；`tools/verify_package.py`
另外断言 `_internal/` 体积合理、用户数据目录都在启动器旁、且纯用户数据目录
（`subtitles/`、`longform_state/`、`ffmpeg/`）没有混进 `_internal/`。

这里有个容易踩坑的**同名双用途目录**：启动器旁的 `ov_models/` 是用户数据
（按需下载的识别权重，更新时不动），而 `_internal/ov_models/` 是随包只读资源
（Silero VAD、Mel filters，由 `STATIC_DATA` 经 `--add-data` 打进去）。
早期一条按目录名一刀切的规则禁止 `ov_models/` 出现在 `_internal/` 内，与构建脚本和
`app.py::_find_vad_model()` 自相矛盾，曾让 Windows 包在打完 198 MB ZIP 后才于校验步失败。
现在 `check_layout()` 按内容判定：该目录只允许 VAD 与 mel 资源白名单，出现 `.bin` 权重即判失败；
`tests/test_verify_package.py` 用伪造目录树覆盖合法布局与各类越界情形。函数内动态 import
的模块若漏列，不会在启动时报错，而是点到对应功能才 `ImportError`，所以这些校验都是
构建时的硬性检查。

另一个容易漏的体积来源是**界面层**：`app.py` 是 Tk 桌面版，WebView 版只复用它的推理解码
核心（`ASREngine` / `ASREngine1p7B` / `RealtimeManager` 与上方那批纯函数），从不实例化
`App`。但 PyInstaller 是静态分析——只要看到 `import customtkinter`，就会把
customtkinter + tkinter + tcl/tk 全量收进包里。因此整段 GUI（含 `import tkinter`）放在
`if not _WEBVIEW_BUILD:` 里，打包时由 `QWENASR_WEBVIEW_BUILD=1` 屏蔽；直接 `python app.py`
行为不变。这条边界由 `tests/test_webview_bundle.py` 用两个子进程分别验证。

启动器本身还有一条与打包方式强相关的约束：`--windowed` 的 EXE **没有主控台**，
`sys.stdout` / `sys.stderr` 是 `None`。开发模式永远有终端，所以这类问题只在打包版暴露
（曾表现为关窗时 `AttributeError: 'NoneType' object has no attribute 'flush'`）。
`app_webview.hush_stdio()` 在导入期换成写 `launcher.log` 的替身，收尾 flush 改为尽力而为，
未捕获异常统一写日志并弹窗。日志每行带 `[月-日 时:分:秒.毫秒]`，每次启动另有一份
`launcher-<年月日-时分秒>-p<PID>.log` 快照（保留最近 12 份）——同一台机器跑多次时，
只有时间和 PID 能把「崩掉那次」从历史里分出来。


进阶主题（内容寻址 manifest、差量、回滚、冷启动基准、签名与 SmartScreen）见 [打包与升级](打包与升级.md)。

## 3. 统一流式数据流

所有输入（GUI 单文件、批量、CLI、局域网 API）都走同一条 `LongformRunner`
路径，不再按时长分成两套逻辑。

```text
音频 / 视频文件
  → ffmpeg 流式输出 16 kHz / mono / s16le PCM（无 ffmpeg 时 WAV 走标准库回退）
  → 滚动 VAD 缓冲（上限约 32 秒，与文件长度无关）
  → 语音组 → processor_numpy 特征 → OpenVINO INT8 IR → 文本
  → 每组立刻 append 写 SRT / JSONL + 保存 checkpoint
  → SSE 推送结构化进度与实时字幕批次
```

内存占用与音频长度无关：模型权重是固定的常驻成本，流式缓冲是固定小量，
字幕不攒到最后才写盘。段长只影响上下文完整度与总耗时。

### 3.1 为什么 1.7B 的段长上限是 20 秒

`app.py` 里 `ASREngine1p7B.max_chunk_secs = 20` 是**切点质量与速度的折中**，
不是 IR 的形状约束——四个 IR 的输入维度全是动态的（`mel [?]`、
`input_embeds [?,?,?]`、KV 全 `?`），编码器实测可跑到 300 秒。

上限只有一处来源，向下游传播三路：

| 环节 | 代码 | 作用 |
|---|---|---|
| 类属性 | `app.py` `max_chunk_secs = 20` | 唯一来源 |
| VAD 分组 | `vad_groups.detect_speech_groups(…, 20)` | 跨段累积超过 20 秒就断开 |
| 超长段切分 | `chunk_split.split_oversized(…, 20)` | 单段本身超 20 秒时按能量低谷切开 |
| 补零上限 | `LightProcessor(ov_dir, max_secs=20)` | 夹紧天花板，防止意外超长 |

模板里的 `n_samples` / `nb_frames` / `n_audio_tokens` 只用来换算「每秒系数」
（100 帧/秒、13 token/秒），**不再是每次补零的目标值**。实际补零长度是
`ceil(实际秒数)`：

| 段长 | 补到 | mel 帧 | audio token |
|---:|---:|---:|---:|
| 3.8 s | 4 s | 400 | 52 |
| 5.5 s | 6 s | 600 | 78 |
| 10.3 s | 11 s | 1100 | 143 |
| 19.9 s | 20 s | 2000 | 260 |

必须整秒是硬约束（非 100 倍帧数会让 encoder 的 reshape 直接失败），但**只有
整秒**。从前每段都补满上限，等于让 3 秒的段落付 20 秒的算力 —— 600 秒语音
实测：固定补满 391.9 秒 → 按实际长度 381.2 秒（−2.7%）。省得不多，是因为
这段录音的 VAD 组本来就偏长（平均 8 秒）；停顿密集的素材收益会更大。

**20 秒这个数怎么来的**（600 秒真实课程录音，端到端实跑）：

| 配置 | 最终段数 | 硬切刀口 | 耗时 |
|---|---:|---:|---:|
| 旧：cap 10 + 固定补零 + 等长硬切 | 68 | 33 | 391.9 s |
| cap 10 + 动态补零 + 低谷切分 | 73 | 33 | 381.2 s（−2.7%） |
| **新：cap 20 + 动态补零 + 低谷切分** | **40** | **12** | **396.9 s（+1.3%）** |

「刀口」指单段超过上限、必须再切开的次数 —— 每一刀都有机会把一个字劈成
两半（前半和后半分属两次辨识，两边都会错）。20 秒把刀口从 33 降到 12
（−64%），总耗时代价只有 1.3%：短段省下的空转正好抵掉了长段多付的部分。

单段耗时是超线性的：10 秒 4.11 s、15 秒 8.61 s、20 秒 12.48 s、30 秒 21.79 s
（RTF 0.41 → 0.73），因为 KV cache 变长、解码逐步串行。段长增加也让单段内存
线性增长（mel 张量与 KV cache 都按 token 数算），但远小于 4.4 GB 的常驻权重。

完整的输入边界（整秒约束、1 秒下限、300 秒实测通过）见
[模型输入约束](模型输入约束.md)。

### 3.2 可选后处理：词级时间轴与说话人分离

这两项在统一流式时没有删除，而是从旧的整段路径移到了 `postprocess.py`
的 `StreamEnhancer`，挂在同一条流式管道上：

| 功能 | 输入 | 实现 |
|---|---|---|
| 词级时间轴（卡拉OK逐字） | 当前语音组的 PCM chunk + 识别文本 | 写临时小 WAV，调 `engine._align_chunk()`（chatllm ForcedAligner，CPU 子进程），把局部时间平移成全局时间后按行分配 `words` |
| 说话人分离 | 同一份 PCM chunk | 调 `diar_engine._get_embedding()` 每段提一个 256 维向量，只攒向量不攒音频；任务结束时聚类一次，按时间区间给字幕标 `說話者N` |

两者都复用识别时**已在内存里**的 chunk，不需要第二次解码，也不需要把
3–5 小时音频重新读进来。

失败隔离是硬约束：SRT 由 Runner 逐组 append 写盘，是唯一事实源；增强结果
另存 `*.rich.json`，`finalize()` 以 JSONL 为准重建行列表并原子替换。对齐器
崩溃、聚类报错、增强文件写不进去，都只记一条 note，**不会改动或删除任何
一条 SRT 字幕**。界面横幅也写明「失败不影响字幕」。开关勾选但对应模型未
安装时，本次跳过并提示到模型页下载，不自动下载 939 MB 的 ForcedAligner。

## 4. SSE 事件契约

`webview_server._EventHub` 把 `WebBackend` 的事件广播给所有 `/api/events`
订阅者。前端用 `window.QwenAPI.on(event, handler)` 接收。

| 事件 | 载荷 | 用途 |
|---|---|---|
| `progress` | `pct`, `status` | 兼容旧版百分比进度条 |
| `progress-detail` | `pct`, `status`, `taskId`, `doneSec`, `totalSec`, `groups`, `etaSec`, `phase` | 已处理时间 / 总时长、分段数、剩余时间、阶段 |
| `segments` | `taskId`, `count`, `segments[{index,start,end,text}]` | 实时字幕；后端按 0.5 秒或 8 条节流成批 |
| `capabilities` | 生效切分长度、内存预估、`alignAvailable` / `diarAvailable` / `alignActive` / `diarActive` | 任务开始前告知增强功能是否可用、本次是否生效 |
| `vad-preview` | 段长分布、超上限比、极短段比、静音比 | 切分预检结果（前 5 分钟，不跑识别） |
| `download-retry` / `download-failure` / `download-source-switch` | `attempt`, `code`, `hint`, `file`, `provider` | 下载失败分类与可执行下一步 |
| `status` / `tunnel` | 模型状态、隧道状态 | 状态列与端点页 |

下载类事件由 `downloader.py` 的 `set_download_event_hook()` 发出，经
`WebBackend._install_download_hook()` 转接，不再 `print()` 到窗口版 EXE
不可见的 stdout。

`segments` 有节流是必要的：3–5 小时课程会产生上万条字幕，逐条推事件会让
WebView 渲染进程成为新的内存瓶颈。前端同样把实时列表限制在最近 200 条，
并在用户手动上滚时暂停自动跟随。

进度条下方同时给出「时间 / 分段」与「百分比」两种视图；批量页复用同一套
识别参数，并把队列总进度显示在摘要里。

## 5. 模型下载

`models.json` 是唯一事实源，`model_catalog.py` 负责读取与校验、
`catalog_status()` 汇总状态、`build_manifest_text()` 生成下载清单、
`import_local_bundle()` 导入并校验本地模型。始终使用标准库 `urllib`，
不引入 `huggingface_hub` / `modelscope` / `hf_transfer`。

未对远端文件实测过的 `size_bytes` 与 `sha256` 一律为 `null`，界面显示「未知」；
`size_hint` 是源码注释里抄来的约略值，明确标注仅供参考且不用于进度计算。
镜像切换只改写 `huggingface.co` 前缀，GitHub 直链不受影响。

下载核心 `_download_file()` 支持断点续传、`Content-Length` 缺失时用 HEAD
探测或目录给定大小兜底、重试退避、磁盘空间预检、LFS pointer / HTML 错误页
探测，以及把分类后的错误与来源切换通过事件回调送到界面。

## 7. 验证边界

CI 与本地回归测试使用 mock ASR 引擎，不加载真实 OpenVINO 权重；验证的是
调度层、落盘、断点、下载链路与前后端接线，不验证识别准确率。真实模型推理
需要在用户本机执行。
